What to test before you go live

In the order a customer meets it, not the order it was built. Work top to bottom — later sections assume the earlier ones passed. Anything with a red edge will cost you money or credibility if it is wrong; anything with an amber edge involves someone's card.

Built since the questionnaire — these are what you are testing

  • The Stripe webhook now exists. Your note said a test payment would succeed in Stripe and change nothing in the database. That is no longer true: stripe-webhook sets the plan and the credit allowance, and its signature is verified on every request.
  • The September prices are live everywhere: Growth £79, Scale £270, Enterprise £700 flat — on the pricing page, in checkout, in the app's plan table and in plan_catalogue.

01Before you touch anything

Five minutes that make the rest of this recoverable.

  • Take a Supabase backup.Database → Backups. Pro takes daily ones, but take a manual one now so there is a point to return to that you chose.
  • Confirm the project is Pro and not paused.Free projects pause after 7 days idle. Ten founding members finding a dead link is the worst possible first impression.
  • Keep the Stripe sandbox in test mode throughout.Every step below uses sk_test_…. STRIPE_ALLOW_LIVE stays unset until the very end — with a live key and that flag unset, the function refuses to take money rather than taking it by accident.
  • Have the Supabase logs open in a second tab.Edge Functions → the function → Logs. Nearly every failure below explains itself there.

02The database

Follow supabase/README.md for the detail. These are the checks.

  • All three SQL scripts run without error, in order: SETUP.sql, then MIGRATION_003_founding.sql, then MIGRATION_004_credits_and_billing.sql.The SQL editor runs each file as one transaction, so a failure leaves nothing behind. Fix and re-run the whole file.
  • The verification query returns 4, 1, 3, 1. 
    select (select count(*) from plan_catalogue) as plans,
       (select count(*) from credit_packs)   as packs,
       (select count(*) from ai_limits)      as limits,
       (select count(*) from information_schema.tables
         where table_schema='public' and table_name='credit_holds') as holds;
  • Run migration 004 a second time and confirm it still succeeds.It is written to be re-runnable. If it fails on a second run you have a different copy from the one shipped.
  • Check the prices in the database match the prices on the site. 
    select plan, price_pence, credits_included from plan_catalogue order by sort_order;
    Since the September repricing these should read Growth 7900, Scale 27000, Enterprise 70000 pence — and pricing.html, checkout.html and the app's plan table now say £79, £270 and £700 to match. If you change a price again, change the database row and the page together, then redo section 06.
  • If you had already run migration 004 before this version, confirm Scale really moved to £270. 
    select plan, price_pence from plan_catalogue where plan in ('scale','enterprise');
    The catalogue insert will not overwrite a row that already exists, so the script now carries an explicit correction that only fires where the old value is still there. Expect 27000 and 70000.

03Edge Functions and secrets

  • All four functions are deployed, named exactly right.anthropic-proxy, job-worker, create-checkout-session, stripe-webhook. The app builds its URLs from these names; a typo is a 404 that looks like a broken product.
  • JWT verification: ON for anthropic-proxy and job-worker, OFF for the two Stripe functions.This is the single most important setting on the list. With it off on the proxy, anyone who reads your network tab can spend your Anthropic balance.
  • ALLOWED_ORIGIN has no trailing slash and no folder path.Just https://contractiqplatform.co.uk. A trailing slash produces a 403 that presents as the app being broken.
  • Every secret is set: ANTHROPIC_API_KEY, ALLOWED_ORIGIN, STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET.
  • No key appears anywhere except Supabase Secrets.Not in the repo, not in the app, not in a screenshot. Search the repo for sk_ and sk-ant- before you push.

05Sign-up, and the email that has to arrive

  • Connect your own SMTP before testing this.Supabase's built-in mail is rate-limited on Pro as well as Free. Ten founding members in one evening is precisely the pattern that trips it. Resend is the recommendation — free to 3,000 a month, about ten minutes, and you will need to add its SPF and DKIM records at IONOS or the mail lands in spam.
  • Sign up with a real address and confirm the six-digit code arrives within a minute.
  • Sign up with a corporate address on a different domain.Corporate filters are where verification mail actually dies. A personal Gmail proves very little.
  • Check Authentication → URL Configuration includes your folder path.If it does not, verification links silently do nothing — no error, just a dead click.
  • Type a password by hand rather than pasting it.A remount bug once made the field accept one character at a time, and pasting would never have caught it.
  • After sign-up, open Settings and confirm the plan and credit balance are shown.A new account with no payment should read Evaluation Sandbox, 150 credits. If it says Enterprise, the app is not reading the database.

06Taking a payment

Your steps, with the webhook added — that is the part that was missing.

  • 1 · Deploy create-checkout-session.Supabase → Edge Functions → Deploy a new function → Via Editor. Name it create-checkout-session and paste the file in. Turn off "Enforce JWT verification", because buyers are not signed in yet.
  • 2 · Add the secrets.Edge Functions → Secrets: STRIPE_SECRET_KEY = your sk_test_… key from the Stripe sandbox (Developers → API keys). ALLOWED_ORIGIN is already set and gets reused.
  • 3 · Deploy stripe-webhook and register it in Stripe.JWT verification OFF. Then Stripe → Developers → Webhooks → Add endpoint, URL https://<project-ref>.supabase.co/functions/v1/stripe-webhook, events checkout.session.completed, invoice.payment_succeeded, invoice.payment_failed, customer.subscription.deleted, customer.subscription.updated. Copy the signing secret into STRIPE_WEBHOOK_SECRET. Without this, the payment succeeds and nothing in your product changes.
  • 4 · Send a test webhook from Stripe and get a 200. 
    select id, type, received_at from stripe_events order by received_at desc limit 5;
    A 400 saying "Signature verification failed" means the signing secret is wrong — it is easy to copy the API key by mistake.
  • 5 · Run the site locally and open the pricing page. 
    cd "$HOME/Desktop/2026 - Months/September/ContractIQ_GitHub_FullApp_v9" && python3 -m http.server 8000
    Then http://localhost:8000/pricing.html. Localhost is allowed automatically while the Stripe key is a test key, so you do not need to touch ALLOWED_ORIGIN.
  • 6 · Choose Growth or Scale and pay with 4242 4242 4242 4242, any future expiry, any CVC.The payment appears under Payments in your Stripe sandbox.
  • 7 · Confirm checkout will not proceed without all three confirmations.Terms, "buying for a business with authority", and the AI limitations notice. Self-serve has no signed Order Form, so these are where those confirmations now live — and without the business confirmation, consumer cancellation rights apply by default.
  • 8 · Confirm the payment reached the database. 
    select email, plan, claimed_at from pending_subscriptions order by created_at desc limit 5;
    A row with claimed_at null is correct: the buyer has no login yet, so the payment is parked against their email.
  • 9 · Now sign up with the same email address and confirm the plan applies itself. 
    select plan, credits_included, stripe_customer_id, billing_status from accounts
 order by created_at desc limit 3;
    This is the whole customer journey and the step most likely to be skipped. Growth should read 500 credits.
  • 10 · Sign up with a different email and watch it not apply.Expected behaviour, and worth seeing once so you recognise the support ticket. The fix is one UPDATE, in the README.
  • 11 · Optional: use your own Stripe products.If you have created ContractIQ products and prices in Stripe, put their ids into plan_catalogue.stripe_price_id and credit_packs.stripe_price_id and those are used instead of prices created on the fly.
  • 12 · Cancel the subscription in Stripe and confirm the account drops to sandbox.
  • 13 · Trigger a failed payment in Stripe and confirm the account is marked past_due but keeps working.Stripe retries for days. Cutting someone off over an expired card is how you lose a customer you had already won.

07Credits — the part that decides whether this is a business

  • Run one analysis and confirm exactly 10 credits are deducted, not 50.An analysis is five calls to the model. They share a run id so the run is charged once. Verified automatically, but check it against a real analysis too.
  • Confirm the balance drops while the analysis is running, and the ledger row appears only when it finishes. 
    select * from credits_breakdown('<your-account-id>');
select created_at, kind, source, credits from my_credit_history limit 10;
  • Make an analysis fail and confirm nothing is charged.Easiest way: temporarily set ANTHROPIC_API_KEY to rubbish. The reserved credits must come back.
  • Ask Cedric a question and confirm 2 credits are deducted.Cedric was entirely unmetered until now.
  • Run an account down to zero and confirm the block is a panel, not a toast, naming the cost, the balance and offering to buy credits.
  • Buy the 100-credit pack for £25 with the test card, and confirm the balance rises within a few seconds of returning.
  • Confirm bought credits survive a plan reset, and plan credits are spent first. 
    select plan_left, bolton_left, total_left from credits_breakdown('<account-id>');
    Verified automatically — a 10-credit spend with 5 plan credits left took 5 from the plan and 5 from the bought balance. Worth seeing once in the product.
  • Run 21 analyses in an hour and confirm the 21st is refused.The limit is per workspace, held in ai_limits, and survives a function cold start. Change the number there, not in code.

08Trying to break it on purpose

Each of these was possible before this round of work.

  • Call the proxy with no session and confirm a 401. 
    curl -i -X POST https://<project-ref>.supabase.co/functions/v1/anthropic-proxy \
  -H "content-type: application/json" \
  -d '{"messages":[{"role":"user","content":"hello"}]}'
    If this returns an answer from Claude, JWT verification is off and your balance is public.
  • Call it from a different origin and confirm a 403.
  • Open two browser tabs on a workspace with 10 credits and start an analysis in both.One must succeed and one must be refused. Both succeeding means the reservation lock is not working.
  • Sign in as a second user in another workspace and confirm you cannot see the first one's contracts.
  • POST a fake event to the webhook URL and confirm a 400.Without signature verification, anyone could grant themselves an Enterprise plan.

11What is still not done

Nothing persists yet. This is the one remaining launch blocker and the reason the audit scored 4/10. Contract records, documents and analyses still live in browser memory and are lost on refresh — after you have paid Anthropic for the analysis. The credits are now real, the plan is real and the payment is real; the work product is not saved. That is the next piece of work, and it is the long one.
Also outstanding. No self-service billing portal — cancellations come to you by email, and success.html now says so rather than pretending otherwise. No SMTP connected yet. Six placeholders remain in the Legal Centre. The sign-up screen inside the app still uses the old single "accept the terms" checkbox; the three confirmations were added at checkout, and sign-up should match it.
A smaller one worth knowing. Where a user belongs to more than one workspace, the app picks the first it finds. There is no workspace switcher, so today that is invisible — but it will need solving before anyone is a member of two.
